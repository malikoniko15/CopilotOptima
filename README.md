# AI Cost Tracker

Корпоративный шлюз для API OpenAI / Anthropic и дашборд контроля расходов. React + TypeScript + Vite + TailwindCSS, FastAPI + httpx, Supabase PostgreSQL / Auth.

## Быстрый просмотр

Нужны Node.js 22.12+ и npm. В корне проекта:

```powershell
npm install
npm run dev
```

Откройте http://localhost:5173. Без переменных Supabase интерфейс открывается в **явно обозначенном деморежиме**: графики, фильтры, CSV, создание сотрудника, изменение лимита и карантин доступны без внешних сервисов. Тестовые ключи не работают с API; изменения исчезают после перезагрузки. В демонстрации нет реальных расходов или пользователей.

## Рабочий режим

### 1. Supabase

Создайте проект и выполните [supabase/schema.sql](supabase/schema.sql) в SQL Editor **один раз**. Скрипт создаёт таблицы `users`, `api_logs`, представление `user_finances` и функции резервирования / расчёта. Схема использует PostgreSQL 15+.

Если проект был развёрнут до появления проверки VPN IP, один раз выполните [supabase/migrate_vpn_cidr.sql](supabase/migrate_vpn_cidr.sql). После миграции существующие сотрудники не смогут отправлять новые запросы, пока администратор не укажет их VPN IP с маской в «Сотрудники и ключи».

В Authentication → Users создайте администратора с email / паролем. Назначьте роль через SQL Editor, подставив его email:

```sql
update auth.users
set raw_app_meta_data = coalesce(raw_app_meta_data, '{}'::jsonb)
  || '{"role":"admin"}'::jsonb
where email = 'admin@your-company.com';
```

После назначения роли выйдите и войдите снова. Не используйте `user_metadata` для полномочий: пользователь может менять эти данные сам. Backend проверяет сессию через Supabase Auth `/auth/v1/user` при каждом административном запросе. Публичная регистрация в интерфейсе не предусмотрена.

### 2. Backend

Python 3.11+. Команды из корня проекта, PowerShell:

```powershell
python -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r backend/requirements.txt
Copy-Item backend/.env.example backend/.env
Copy-Item backend/pricing.example.json backend/pricing.json
```

Заполните `backend/.env`:

| Переменная | Назначение |
| --- | --- |
| `SUPABASE_URL` | HTTPS URL проекта Supabase |
| `SUPABASE_KEY` | Серверный legacy `service_role` JWT, никогда не `anon` |
| `OPENAI_API_KEY` | Корпоративный ключ OpenAI |
| `ANTHROPIC_API_KEY` | Корпоративный ключ Anthropic, если используете его |
| `CORS_ORIGINS` | Разрешённые адреса frontend через запятую |
| `PRICING_FILE` | Путь к JSON тарифов относительно `backend/` |

В `backend/pricing.json` укажите разрешённые модели и **проверенные вами** тарифы в USD за 1 млн токенов. `pricing.example.json` содержит иллюстративные значения; это не автоматически актуализируемый прайс-лист. Пример не загружается сервером автоматически. Если рабочего файла нет, все модели отклоняются до вызова провайдера. После изменения тарифов перезапустите сервер. Исторический тариф сохраняется в каждой записи запроса.

```powershell
.\.venv\Scripts\python.exe -m uvicorn backend.main:app --reload --host 127.0.0.1 --port 8000
```

Backend проверяет сетевой IP подключения, а не произвольный `X-Forwarded-For`. Если он находится за reverse proxy, разрешите proxy-заголовки только от адреса этого proxy, например: `--proxy-headers --forwarded-allow-ips=10.0.0.10`. Не используйте `*` для публично доступного backend: поддельный заголовок сможет обойти VPN-проверку.

API: http://localhost:8000/docs. `GET /health` проверяет только доступность процесса, а не провайдеров и базы. На Linux/macOS используйте `.venv/bin/python` и `cp` вместо PowerShell-команд.

### 3. Frontend

```powershell
Copy-Item .env.example .env
```

Укажите `VITE_SUPABASE_URL` и `VITE_SUPABASE_ANON_KEY` (публичный anon / publishable key). **Нельзя помещать Master-Key или service_role в переменные `VITE_*`: они попадут в браузер.** Если заполнена только одна переменная Supabase, приложение показывает ошибку конфигурации, а не демоданные.

В разработке Vite проксирует `/api` на `http://127.0.0.1:8000`. Для production задайте `VITE_API_URL` (HTTPS-адрес backend без `/api`) или настройте reverse proxy для `/api`. Добавьте реальный origin frontend в `CORS_ORIGINS`.

```powershell
npm run dev
# Проверка и production-сборка:
npm run build
```

Войдите администратором, откройте «Сотрудники и ключи», создайте сотрудника и укажите назначенный вашей VPN адрес с маской, например `10.10.9.7/24`. Сервис не назначает и не меняет VPN-адрес: он показывает настройку и при каждом запросе сравнивает фактический IP подключения с адресом сотрудника (`10.10.9.7` в примере). Маска сохраняется как часть конфигурации, но не разрешает другим адресам из `/24` использовать ключ этого сотрудника. Полный ключ показывается один раз; в базе остаются SHA-256 хеш и 12-символьный префикс. Введённый бюджет — сумма в USD на календарный месяц по UTC.

## Использование шлюза

OpenAI SDK (устанавливается отдельно: `pip install openai`):

```python
from openai import OpenAI

client = OpenAI(
    base_url="http://localhost:8000/v1",
    api_key="act_YOUR_VIRTUAL_KEY",
    max_retries=0,  # Не повторяйте неоднозначные таймауты автоматически.
)
response = client.chat.completions.create(
    model="YOUR_CONFIGURED_MODEL",
    messages=[{"role": "user", "content": "Привет!"}],
    max_completion_tokens=256,
)
print(response.choices[0].message.content)
```

Anthropic: отправьте `POST http://localhost:8000/v1/messages` с `x-api-key: act_YOUR_VIRTUAL_KEY`, `Content-Type: application/json` и JSON:

```json
{
  "model": "YOUR_CONFIGURED_ANTHROPIC_MODEL",
  "max_tokens": 256,
  "messages": [{"role": "user", "content": "Привет!"}]
}
```

Поддерживается ограниченный текстовый поднабор API: `model`, строковые `messages`, `stream: false`, `temperature` и лимит выходных токенов. Для Anthropic `system` передаётся отдельной строкой. По умолчанию выход ограничен 1024 токенами; максимум — 16384. Неизвестные параметры, инструменты, изображения, аудио, structured outputs, несколько ответов (`n`), стриминг и Responses API явно отклоняются. Это не полная замена всех возможностей SDK.

## Как устроены расчёты и безопасность

1. Прокси хеширует виртуальный ключ. SQL-функция под блокировкой строки сотрудника проверяет ключ, фактический IP подключения по настроенной VPN-подсети, карантин и доступный бюджет, затем создаёт `pending`-запись с резервом. Параллельные запросы учитывают общий резерв.
2. Прокси отправляет запрос только на фиксированный HTTPS endpoint выбранного провайдера, подставляя Master-Key из окружения. Входящие заголовки клиента не пересылаются; редиректы и автоматические повторы отключены.
3. По `usage` рассчитывается стоимость с `Decimal`, отдельно учитывается кешированный вход. Расчёт финализируется идемпотентной SQL-функцией. Ответ успешного провайдера возвращается без изменения тела.
4. Сохраняются сотрудник, время, провайдер, модель, тарифы, токены, стоимость, резерв, длительность, статус и ID запроса провайдера (когда известен). Промпты, ответы и полные ключи не записываются в БД. Ошибки валидации и upstream-ошибки не отражают содержимое запроса или ключи.

Запись расчёта использует асинхронный I/O, но **ожидается до возврата ответа**, чтобы не оставлять финансовый учёт на ненадёжную фоновую задачу. Если финализация недоступна, успешный ответ всё равно возвращается с `X-Accounting-Status: pending`, а резерв сохраняется. `X-Request-ID` помогает найти запись.

Таймаут, upstream 408 / 5xx, неизвестный формат `usage` или незавершённый запрос сохраняют резерв: отсутствие ответа не означает отсутствие списания. Явный upstream 4xx (кроме 408) освобождает резерв. Старые `pending` не снимаются автоматически, в том числе при смене месяца. Проверяйте их по данным провайдера и завершайте через `settle_request` в SQL Editor с подтверждёнными токенами / стоимостью. Для примера вызова используйте сигнатуру в schema.sql; после успешного расчёта повторное списание невозможно. Автоматическая сверка и очередь повторной доставки расчётов в MVP отсутствуют.

Резерв для текстового входа рассчитан по UTF-8 размеру с запасом; **это не точная токенизация и не абсолютная гарантия непревышения лимита**. Фактическое списание может оказаться выше резерва; следующий запрос тогда блокируется. Для жёсткого финансового лимита нужна точная оценка для поддерживаемой модели и дополнительный лимит у провайдера. Финансовый расчёт также зависит от правильности настроенных тарифов; неподдерживаемые типы биллинга нельзя считать точным аналогом счёта провайдера.

Карантин проверяется в БД при каждом новом запросе без кеша. Запрос, уже допущенный / отправленный провайдеру, может завершиться. RLS включён; `anon` и `authenticated` не имеют прямого доступа к таблицам, представлению и функциям. Backend действует через service_role после собственной авторизации.

Это MVP для одного корпоративного пространства. Для публичного production-развёртывания потребуются HTTPS, rate limiting / ограничения соединений, мониторинг зависших резервов, резервные копии и управляемое хранение секретов. Прокси не отменяет политику хранения данных самим провайдером. Интерфейс показывает до 20 000 запросов за 60 календарных дней и до 5 000 сотрудников; при достижении границы явно предупреждает о неполной выборке. Месячные балансы рассчитываются БД по всем записям.

Неиспользуемый API-доступ не означает платную подписку: инсайт о неактивных сотрудниках показывает нераспределённую пользу от лимитов, а не обещанную экономию на лицензиях.

## Проверки

```powershell
.\.venv\Scripts\python.exe -m unittest backend.test_gateway -v
npm run build
npm run test:sql
npx playwright install chromium
`npm run test:e2e`
```

Если установлен Microsoft Edge, можно использовать его без загрузки Chromium:

```powershell
$env:PW_CHANNEL = 'msedge'
npm run test:e2e
```

Тесты backend используют подменённые HTTP-ответы: они не тратят API-кредиты и не требуют Supabase. Проверяются цена с кешем, подмена ключей, приватность логов, блокировка доступа, лимиты, неоднозначные ошибки, финализация и авторизация администратора. SQL-тесты запускают настоящую схему в PostgreSQL через PGlite в памяти: резерв, повторную финализацию, смену месяца, карантин и запрет доступа для anon/authenticated. PGlite не моделирует конкуренцию нескольких серверных соединений. Браузерные тесты проверяют фильтры / экспорт, жизненный цикл сотрудника и мобильную навигацию. Перед эксплуатацией проверьте полный сценарий и конкурентные запросы на собственном Supabase и с собственным ключом провайдера.

## Официальные источники интеграции

Формат Chat Completions, `usage` и лимит ответа сверены с [OpenAI API Reference](https://developers.openai.com/api/reference/resources/chat). Доступ к таблицам спроектирован с учётом [Supabase Row Level Security](https://supabase.com/docs/guides/database/postgres/row-level-security); полномочия администратора проверяются через [Supabase Auth](https://supabase.com/docs/guides/auth/users). Тарифы и доступность конкретных моделей необходимо отдельно сверить перед рабочим запуском.
